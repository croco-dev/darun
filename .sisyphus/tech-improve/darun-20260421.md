# Darun 기술 건강도 진단 리포트

> 날짜: 2026-04-21
> 범위: darun 모노레포 전체 (apps/*, libs/*)
> 브랜치: tech-improve-darun

---

## TL;DR

darun 모노레포는 pnpm workspace + Turborepo 기반의 도메인 분리 구조를 갖추고 있으나, 현재 `pnpm typecheck`와 `pnpm build`가 실패하는 상태다. 핵심 원인은 `@darun/products-feature`의 공개 API 불일치와 `@darun/sanitize`의 JSX 설정 누락이다. 보안 측면에서는 `pnpm audit` critical 4건을 포함한 106건의 취약점이 프로덕션 런타임 체인에 걸려 있어 즉시 대응이 필요하다.

구조적으로는 feature 간 직접 의존, 다수 도메인의 placeholder 계층, 테스트 공백이 유지보수 비용을 높이는 방향으로 누적되고 있다. 성능 축은 정적 분석만 수행했으므로 실측 전까지 확정 판단을 보류한다.

**즉시 조치 필요:** F3(보안 취약점), F1(typecheck/build 실패), F2(typecheck 실패)

## 판단 기준 출처

모든 발견은 다음 두 가지 출처만 사용했다.

1. **코드베이스 내부 패턴**: 실제 파일 읽기, `pnpm lint/typecheck/test/build` 실행 결과, `pnpm audit` 출력
2. **업계 표준**: OWASP 의존성 취약점 관리, Clean Architecture 레이어/경계 분리, 테스트 피라미드, TypeScript strict 모드 권고, 신뢰 가능한 CI signal 원칙

외부 벤치마크, 경쟁사 비교, 주관적 선호는 판단 근거에서 제외했다.

## Architecture

### 확인됨: 정상 패턴

**domain -> datasource -> feature/app 진입점 분리가 기본 골격으로 유지됨**

- `libs/accounts/domain/src/index.ts`: repository token/entity/usecase만 export
- `libs/accounts/datasource/src/index.ts`: Firebase/PostgreSQL 구현체만 export
- `apps/graphql-api/src/app/resolvers.ts`: app 레벨에서 `@darun/*-feature/server`만 조립
- `libs/shared/provider-database`, `provider-auth/server`, `provider-auth/client`: 횡단 인프라를 별도 패키지로 분리

**dual export(`.` + `./server`) 패턴이 GraphQL/SSR 진입점을 분리하는 공통 규약으로 쓰임**

- `libs/products/feature/package.json`: `.` -> `src/index.ts`, `./server` -> `src/server.ts`
- 동일 패턴: `companies-feature`, `images-feature`, `translation-feature`
- 앱 소비처: `apps/graphql-api/src/app/resolvers.ts`, `apps/*/app/server.tsx`

### 확인됨: 구조 리스크

**`products-feature`가 타 도메인 feature/server에 직접 의존해 feature 계층 간 결합이 생김**

- `libs/products/feature/package.json`: `@darun/companies-feature`, `@darun/translation-feature` 직접 의존
- `Product.query.resolver.ts:2`: `@darun/companies-feature/server`에서 `Company` import
- `Product.mutation.resolver.ts:19`: `@darun/translation-feature/server`에서 `TranslationJobService` import
- `.cursor/rules/000-core-architecture.mdc`는 크로스 도메인 직접 참조를 금지하지만 ESLint가 포착하지 못함

**빈 계층(`export {}`)이 여러 도메인에서 반복되어 service/feature/ui 레이어가 placeholder 상태로 남아 있음**

확인된 빈 진입점:
- `libs/accounts/feature/src/index.ts`, `libs/accounts/service/src/index.ts`
- `libs/products/service/src/index.ts`, `libs/products/ui/src/index.ts`
- `libs/search/feature/src/index.ts`, `libs/search/service/src/index.ts`
- `libs/companies/service/src/index.ts`, `libs/images/service/src/index.ts`
- `libs/recommendation/feature/src/index.ts`

### 가설: 구조 리스크

**service 계층이 일부 도메인에서 사실상 비활성화되어 `domain -> feature` 직결이 기본 흐름일 가능성**

- `libs/products/service/package.json`, `libs/search/service/package.json`: domain만 의존하지만 공개 진입점은 `export {}`
- `Product.query.resolver.ts`, `Product.mutation.resolver.ts`: domain usecase를 feature가 직접 주입받음
- 단, DI 조립 파일 전체를 추적하지 않았으므로 "service가 완전히 불필요하다"까지는 단정하지 않음

**재확인 근거:** 샘플 영역(`accounts`, `products`, `shared/provider-*`) + 추가 영역(`search`, `images`, `companies`, `translation`, `apps/graphql-api`) 모두에서 동일 패턴 반복 확인됨.

**순환 의존:** 읽은 샘플 범위에서 명시적 순환 import 증거는 없음. 단, 전체 import 그래프를 완전 계산한 것은 아니므로 "모노레포 전체 순환 의존 없음"까지는 주장하지 않음.

- `passWithNoTests: true` 때문에 테스트 없는 패키지도 green으로 집계되어 CI signal 신뢰도가 낮아짐
- E2E는 `apps/service-web`에만 Playwright 설정이 있으나, `tests/` 아래 실제 `.spec.ts` 파일은 현재 부재 (`.gitkeep`, `README.md`, `helpers/auth-mock.ts`만 존재)

## Performance

**N/A (정적 가설만, 실측 부재)**

실제 프로파일링, 번들 분석, 응답 시간 계측, Apollo cache hit rate, DB query count, resolver별 tracing이 수행되지 않았다. 아래는 정적 구조 분석에서 도출한 가설이며, 실측 전까지 확정 심각도를 부여하지 않는다.

**정적 가설 목록 (참고용)**

5. `getServerClient`의 인증 쿠키 의존으로 Next.js 정적 최적화 범위가 줄어들 가능성

**후속 권장:** 위 가설은 번들 리포트, Apollo tracing, DB query count 측정 후 재평가해야 한다.

## Security

### 인증/권한 경계 (확인됨)

- `apps/graphql-api/src/functions/context.ts`: 요청 단위로 `authToken`을 `GetAccount.execute`에 전달, `getUserIdOrThrow()`에서 미인증 시 `Unauthorized` throw
- `libs/accounts/datasource/src/repositories/FirebaseAccountRepository.ts`: Firebase Admin `verifyIdToken(token)` 성공 시에만 계정 복원, 실패 시 `null` 반환
- 클라이언트 UI 상태(`Authorized`/`UnAuthorized`)는 토큰 claim과 서버 검증 결과에 의존하며, UI 상태만으로 권한이 확정되지 않음

### secret 취급 방식 (확인됨)

- `apps/graphql-api/src/config/environment.ts`: `requireEnv()`로 서버측 필수 환경변수 강제, 비밀값은 환경변수 주입
- Cloudinary secret: 런타임 설정에서 읽어 서명 생성에만 사용, secret 없으면 즉시 예외
- `sameSite: 'strict'` 쿠키 정책 공통 사용. 단, `httpOnly`/`secure` 속성은 provider 코드에서 직접 지정되지 않음

### 의존성 취약점 (확인됨, P0)

`pnpm audit` 결과: 총 106건 (critical 4, high 55, moderate 34, low 13)

대표 취약 경로:
- `apps/graphql-api > firebase-admin > @google-cloud/firestore > form-data <2.5.4`
- `apps/graphql-api > serverless-offline/@aws-sdk > fast-xml-parser <4.5.4`
- `apps/graphql-api > firebase-admin > @google-cloud/firestore > protobufjs <7.5.5`
- `libs/images/datasource > cloudinary <2.7.0`
- `apps/graphql-api > firebase-admin > google-auth-library/jsonwebtoken > jws` 취약 버전
- `apps/graphql-api > serverless > axios <=1.13.4`
- `libs/shared/utils-auth-service/firebase > firebase > @firebase/auth > undici <5.29.0`

취약점이 `graphql-api`와 인증/이미지 업로드 관련 트랜지티브 의존성에 집중되어 있으며, 배포/서버 런타임 체인이 직접 영향권에 있다.

### 저장소 위생 리스크 (확인됨, P2)

- `apps/graphql-api/.env`가 추적 파일로 존재함. 실제 비밀값 포함 여부는 이번 범위에서 읽지 않았으나, 추적 대상 경로에 `.env` 파일이 있다는 사실 자체가 협업/운영 리스크

## DX

### 장점

- `README.md`, `package.json`, `turbo.json`, `PullRequest.yaml`이 `pnpm install/dev/lint/typecheck/test` 흐름을 기준선으로 공유
- `prepare: lefthook install`로 `pnpm install` 후 훅 설치 자동 연결
- `Deploy.yaml`/`Production.yaml`은 GitHub Secrets를 통해 배포용 환경변수를 주입해 secret 전달 경로가 저장소 밖으로 분리됨
- `.env.sample` 파일이 필수 키 목록을 제공해 온보딩에 도움

### 약점

- README의 품질 스택 설명은 `Vitest, Biome` 중심이지만, 실제 훅/검증은 `eslint` 중심 (문서-도구 불일치)
- 루트 `format` 스크립트가 `turbo lint -- --fix`라서 이름은 format이지만 실제 수행체는 lint fix (명명 혼동)
- `lefthook.yml` pre-commit은 staged 파일의 eslint --fix만 실행하고 typecheck/test는 CI에만 의존 (로컬-원격 검증 강도 차이)
- `vitest.config.ts`의 `passWithNoTests: true`로 테스트 없는 패키지도 green 집계
- 배포 워크플로우(`Deploy.yaml`, `Production.yaml`)는 `pnpm install` 후 바로 deploy로 진입하며 lint/typecheck/test를 재검증하지 않음
- 앱별 필수 환경변수 설명표 부족으로 설치 후 어떤 변수를 어디에 채워야 하는지 추론 필요

## tech_contract 권고

아래는 이번 진단 결과를 바탕으로 한 권고 사항이다. 확정 계약이 아니며, 팀 논의와 우선순위 조정 후 적용 여부를 결정해야 한다.

### 즉시 권고 (P0/P1 대응)

1. **의존성 취약점 정리**: `pnpm audit --fix` 또는 영향 패키지 버전 업그레이드를 통해 critical 취약점부터 해소. `firebase-admin`, `serverless`, `cloudinary`, `undici` 연쇄 경로 우선 확인 권장
2. **`@darun/products-feature` 공개 API 복구**: `useProductInfo` re-export 경로와 `ProductLinkTable` export를 `src/index.ts`에 올바르게 연결해 typecheck/build gate 복구
3. **`@darun/sanitize` JSX 설정 추가**: `tsconfig.json`에 `"jsx": "react-jsx"` (또는 프로젝트 규약에 맞는 값) 추가

### 중기 권고 (P2 대응)

4. **feature 간 직접 의존 해소**: `products-feature`의 `companies-feature/server`, `translation-feature/server` 직접 의존을 app 조립 계층으로 이동하거나 공유 인터페이스로 추상화. boundaries descriptor 완성으로 ESLint 경계 검사 실효성 확보
5. **placeholder 계층 정리**: 각 도메인의 `export {}` 계층이 의도적 placeholder인지 미완성인지 팀 내 명시적 결정. 미완성이면 구현 또는 패키지 제거, 의도적이면 README/주석으로 명시
6. **테스트 공백 축소**: feature/service/datasource 계층 중 변경 빈도가 높은 패키지부터 단위 테스트 추가. `echo 1`/`No tests yet` 패키지 중 우선순위 선정
7. **CI signal 신뢰도 개선**: `passWithNoTests: true` 유지 여부 재검토. `libs/voting/domain`, `libs/magazines/domain`처럼 테스트 파일은 있으나 스크립트가 `echo 1`인 패키지의 실행 경로 연결
8. **`.env` 추적 해제**: `apps/graphql-api/.env`를 `.gitignore`에 추가하고 저장소 히스토리에서 제거. `.env.sample`만 추적 유지

### 장기 권고 (P3 대응)

9. **DX 문서 정합성**: README의 품질 스택 설명을 실제 도구(eslint)에 맞게 수정. `format` 스크립트 명명 정리. 앱별 필수 환경변수 설명표 추가
10. **pre-commit 강화**: `lefthook.yml`에 typecheck 또는 영향 범위 한정 typecheck를 추가해 로컬-CI 검증 강도 차이 축소 (성능 영향 고려 후 결정)
