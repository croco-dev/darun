# Task 8 - 6축 결과 합성 및 심각도/Priority 정규화

정규화 원칙
- P0: 보안/데이터 손실 급. 이번 작업에서는 `pnpm audit` critical 취약점이 실제 프로덕션 런타임 체인에 연결된 경우만 허용.
- P1: 빌드/typecheck/배포 가능성에 직접 영향.
- P2: 유지보수 비용 증가가 예상되는 구조/품질 리스크.
- P3: DX 마찰, 문서 불일치, 경고 레벨, 국소 품질 예외.
- N/A: 측정/평가 불가. 정적 단서만 있고 실측이 없는 경우.
- 중복 통합 원칙: 동일 원인·동일 공개 API·동일 검증 실패로 이어지는 발견은 하나로 묶었다.

## 중복 통합 메모

- `products-feature` 관련 발견은 두 갈래로 정리했다.
  - F1: 실제 gate 실패(typecheck/build)를 만든 공개 API 불일치
  - F4: 그 배경이 되는 경계 약화(feature 간 직접 의존 + boundaries 미완성)
  - 이유: 같은 패키지에서 출발하지만 하나는 즉시 실패, 다른 하나는 구조 리스크라 우선순위와 대응 방식이 다르다.
- 테스트 축은 두 갈래로 나눴다.
  - F7: 테스트 공백의 범위
  - F8: green signal 왜곡 메커니즘
  - 이유: 공백 자체와 신호 신뢰도 저하는 서로 다른 개선 단위다.
- Performance 축은 개별 가설을 쪼개지 않고 F9 하나로 묶었다.
  - 이유: 이번 범위의 공통 결론이 “실측 전까지 확정 불가”이기 때문이다.
