Task 4 - Code Quality 축 진단

## 설정상 기대
- `eslint.config.mjs`
  - `boundaries/element-types`가 활성화되어 `domain -> domain`, `feature -> feature` 직접 참조를 기본적으로 금지해야 한다.
  - React 대상 경로에는 `eslint-plugin-react-compiler` 권장 규칙이 적용되어 메모이제이션 불가능 API 사용을 경고해야 한다.
- `tsconfig.json` -> `libs/shared/utils-tsconfig/tsconfig.base.json`
  - TypeScript `strict: true`로 타입 안정성을 기본값으로 둔다.
  - 다만 `strictPropertyInitialization: false`, `noUnusedLocals: false`, `noUnusedParameters: false`라서 일부 품질 이탈은 컴파일러가 직접 막지 않는다.
- `README.md`
  - 공식 검증 흐름은 `pnpm lint`, `pnpm typecheck`, `pnpm test`이며, lint/typecheck 통과가 기본 품질 게이트다.

## 실제 코드 패턴

### 1) 타입 안정성 - 객관적 위반/완화 흔적
- `apps/admin-web/features/products/NewProductLinkSection/NewProductLinkSection.tsx:12-13`
  - `eslint-disable-next-line @typescript-eslint/no-explicit-any`와 함께 `({ form }: any)`를 사용한다.
  - strict 모드 기대와 달리 실제 런타임 입력 경계를 `any`로 열어 둔 명시적 예외다.
- `libs/shared/utils-apollo-server/src/libs/createLambdaHandler/createLambdaHandler.ts:1`
  - 파일 상단에서 `@typescript-eslint/no-explicit-any`를 파일 단위로 비활성화한다.
  - 현재 본문에는 직접 `any`가 보이지 않지만, 규칙 우회 자체가 타입 안전성 정책 완화 신호다.
- `grep '\bany\b'` 결과
  - 다수의 `__generated__` GraphQL 파일에서 `publishedAt?: any | null`, `startAt?: any | null` 같은 타입이 반복된다.
  - 예: `libs/products/shell/src/components/ProductCompany/__generated__/useProductCompany.ts:12`, `libs/products/feature/src/PublishProductButton/__generated__/usePublishProductButton.ts:15`
  - 수동 작성 코드보다 생성 코드에 집중되어 있어 즉시 P1로 보긴 어렵지만, 스키마/코드젠 경계에서 타입 정밀도가 무너지고 있다는 객관적 신호다.

### 2) 경계 규칙 - 설정과 실제 적용 범위의 간극
- `eslint.config.mjs:37-61`
  - boundaries 규칙은 선언되어 있으나, 실제 lint에서는 아래 경고가 반복된다.
- `pnpm lint` 결과
  - `@darun/products-feature`, `@darun/magazines-feature`, `@darun/companies-feature`, `@darun/ui-admin`, `@darun/utils-image-upload`, `@darun/products-ui`에서
    `[boundaries][warning]: Please provide element descriptors using the 'boundaries/elements' setting.`
  - 규칙은 존재하지만 element descriptor가 충분히 제공되지 않아 경계 검사가 완전하게 작동하지 않는 구간이 있다는 뜻이다.
- `libs/products/feature/src/Product.query.resolver.ts:1-21`
  - products feature가 `@darun/companies-domain`, `@darun/recommendation-domain`, `@darun/search-domain`, `@darun/translation-domain`, `@darun/voting-domain`까지 직접 의존한다.
  - 아키텍처 문서(`.cursor/rules/000-core-architecture.mdc`)는 크로스 도메인 직접 참조를 금지하고 이벤트/조합 계층을 기대하지만, 현재 ESLint 규칙은 이 패턴을 오류로 막지 못했다.
  - 따라서 이것은 "규칙이 있다고 해서 실제로 포착되는 것은 아님"을 보여주는 코드 근거다.

### 3) 코드 스멜 - lint 경고와 실제 코드 연결
- `libs/products/feature/src/ProductListTable/ProductListTable.tsx:59`
  - `useReactTable()` 사용으로 `react-hooks/incompatible-library` 경고가 발생한다.
  - lint는 PASS(에러 없음)지만, React Compiler 관점에서는 메모이제이션 안정성이 약한 훅 사용이 감지된다.
  - 설정(react compiler 권장 룰)과 실제 코드 패턴이 연결된 대표 사례다.
- `apps/graphql-api/src/config/firebase.ts:14,20`
  - 운영 코드에 `console.log`가 남아 있다.
  - `apps/graphql-api/scripts/seed-e2e.ts`의 `console.log`는 스크립트 성격상 허용 가능성이 높지만, `src/config` 내부 로그는 애플리케이션 레이어의 로깅 정책이 명확히 강제되지 않음을 보여준다.

## 주관적 선호 vs 객관적 위반 분리

### 객관적 위반/근거 강한 항목
- `NewProductLinkSection`의 `any` 사용 + ESLint 비활성화
- boundaries 플러그인 descriptor 누락 경고로 인한 경계 검사의 불완전성
- `ProductListTable`의 react-compiler 경고

### 주관적 선호 또는 낮은 확신 항목
- `console.log` 자체는 프로젝트 로깅 정책 부재 상태에서 곧바로 높은 심각도로 단정하기 어렵다.
- 생성 코드의 `any`는 코드젠 설정 한계일 수 있어 수동 코드의 동일 사례와 같은 심각도로 다루면 과대평가다.

## 현재 판단
- 최소 3개 영역이 확인되었다: 타입 안정성, 경계 규칙, 코드 스멜.
- 품질 게이트는 동작하지만, boundaries 설정 미완성과 코드젠 `any` 같은 영역은 "통과"와 "안전"이 동일하지 않음을 보여준다.
