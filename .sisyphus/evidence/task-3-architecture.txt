Task 3: Architecture 축 진단

샘플링 근거
- 깊게 읽은 영역: `libs/accounts/*`, `libs/products/*`, `libs/shared/provider-*`
  - 이유: 계획 파일이 우선 샘플로 지정했고, 도메인/데이터소스/피처/서비스 계층이 모두 드러난다.
- 얕게 재확인한 영역: `libs/search/*`, `libs/images/*`, `libs/companies/*`, `libs/translation/*`, `apps/graphql-api/*`
  - 이유: 샘플 외 최소 1개 이상 패키지/앱에서 같은 경향이 반복되는지 확인하기 위함.

모노레포 경계 근거
- 워크스페이스는 `apps/*`, `libs/*/*`, `libs/shared/*`, `libs/shared/*/*`를 패키지 경계로 사용한다 (`pnpm-workspace.yaml:1-5`).

발견 1
- 구분: 확인됨
- 유형: 정상 패턴
- 제목: `domain -> datasource -> feature/app` 진입점 분리가 기본 골격으로 유지됨
- 근거:
  - `libs/accounts/domain/src/index.ts:1-10`는 repository token/entity/usecase만 export한다.
  - `libs/accounts/datasource/src/index.ts:1-3`는 Firebase/PostgreSQL 구현체만 export한다.
  - `libs/products/datasource/src/index.ts:1-8`는 `Postgresql*Repository`, `ProductDescriptionGeneratorImpl` 같은 구현체를 노출한다.
  - `apps/graphql-api/src/app/resolvers.ts:3-12`는 app 레벨에서 `@darun/*-feature/server`만 모아 resolver를 등록한다.
  - `libs/shared/provider-database/src/index.ts:1-5`, `libs/shared/provider-auth/server/src/index.ts:1-2`, `libs/shared/provider-auth/client/src/index.ts:1-3`는 provider를 횡단 인프라 패키지로 분리한다.
- 영향:
  - 앱이 domain/datasource 구현 세부사항 대신 feature/provider 진입점에 의존하는 기본 레이어링은 살아 있다.

발견 2
- 구분: 확인됨
- 유형: 구조 리스크
- 제목: `products-feature`가 다른 도메인 feature/server에 직접 의존해 feature 계층 간 결합이 생김
- 근거:
  - 패키지 의존성: `libs/products/feature/package.json:24-28`에 `@darun/companies-feature`, `@darun/translation-feature`가 직접 들어 있다.
  - 코드 의존성:
    - `libs/products/feature/src/Product.query.resolver.ts:2` → `@darun/companies-feature/server`에서 `Company` import
    - `libs/products/feature/src/Product.mutation.resolver.ts:19` → `@darun/translation-feature/server`에서 `TranslationJobService` import
  - 반면 datasource는 domain/provider에만 의존한다:
    - `libs/products/datasource/src/repositories/PostgresqlProductRepository.ts:1-4`
    - `libs/products/datasource/src/repositories/PostgresqlCategoryRepository.ts:1-3`
- 영향:
  - feature가 다른 feature의 server export를 소비하면서 도메인 경계가 느슨해지고, resolver/잡 서비스 변경이 인접 feature에 전파될 수 있다.
  - 특히 `Company` graph 타입과 `TranslationJobService`가 재사용되면서 app 조립 계층이 아닌 feature 내부에서 교차 조합이 일어난다.

발견 3
- 구분: 확인됨
- 유형: 구조 리스크
- 제목: 빈 계층(`export {}`)이 여러 도메인에서 반복되어 service/feature/ui 레이어가 placeholder 상태로 남아 있음
- 근거:
  - 우선 샘플:
    - `libs/accounts/feature/src/index.ts:1`
    - `libs/accounts/service/src/index.ts:1`
    - `libs/products/service/src/index.ts:1`
  - 샘플 외 재확인:
    - `libs/search/feature/src/index.ts:1`
    - `libs/search/service/src/index.ts:1`
    - `libs/companies/service/src/index.ts:1`
    - `libs/images/service/src/index.ts:1`
    - `libs/recommendation/feature/src/index.ts:1`
    - `libs/products/ui/src/index.ts:1`
- 영향:
  - 계층은 물리적으로 존재하지만 공개 API가 비어 있어, 의도적 placeholder인지 미완성인지 패키지별로 판단이 필요하다.
  - 특히 `accounts`는 domain/datasource는 존재하지만 feature/service 진입점이 비어 있어 end-to-end 계층 완결성이 끊겨 있다.

발견 4
- 구분: 확인됨
- 유형: 정상 패턴
- 제목: dual export(`.` + `./server`) 패턴이 GraphQL/SSR 진입점을 분리하는 공통 규약으로 쓰임
- 근거:
  - `libs/products/feature/package.json:8-18`는 `.` → `src/index.ts`, `./server` → `src/server.ts`를 분리한다.
  - 동일 패턴 재확인:
    - `libs/companies/feature/package.json:8-18`
    - `libs/images/feature/package.json:7-12`
    - `libs/translation/feature/package.json:7-12`
  - 실제 소비처:
    - `apps/graphql-api/src/app/resolvers.ts:3-12`
    - `apps/admin-web/app/server.tsx:1-2`
    - `apps/service-web/app/server.tsx:1`
    - `apps/visual-web/app/server.tsx:1-2`
- 영향:
  - 서버 전용 resolver/provider를 `./server`로 격리해 앱이 명시적 진입점을 통해 조립하도록 유도한다.
  - 다만 이 패턴이 발견 2처럼 feature 간 직접 server import에도 사용되고 있어, 규약 자체는 정상이나 사용 위치는 주의가 필요하다.

발견 5
- 구분: 가설
- 유형: 구조 리스크
- 제목: service 계층이 일부 도메인에서 사실상 비활성화되어 `domain -> feature` 직결이 기본 흐름일 가능성
- 근거:
  - `libs/products/service/package.json:12-14`, `libs/search/service/package.json:12-14`는 domain만 의존하지만 실제 공개 진입점은 `export {}` 상태다.
  - 실제 feature/resolver는 domain 유즈케이스를 직접 주입받는다:
    - `libs/products/feature/src/Product.query.resolver.ts:3-21, 40-57`
    - `libs/products/feature/src/Product.mutation.resolver.ts:2-22, 54-72`
  - search도 `libs/search/domain/src/index.ts:1-6`, `libs/search/datasource/src/index.ts:1-2`는 존재하지만 feature/service 공개 API는 비어 있다.
- 영향:
  - service 레이어를 둔 설계 의도와 달리 현재 운영 흐름은 domain usecase를 feature가 직접 묶는 구조일 수 있다.
  - 다만 실제 DI 조립 파일 전체를 추적하지는 않았으므로, "service가 완전히 불필요하다"까지는 단정하지 않고 가설로 유지한다.

순환 의존 점검
- 확인됨: 읽은 샘플에서 명시적 순환 import 증거는 찾지 못했다.
- 근거:
  - `products-feature`는 `companies-feature/server`, `translation-feature/server`를 참조하지만, 이번 샘플에서 역방향으로 `products-feature`를 다시 참조하는 import/export는 확인되지 않았다.
  - `apps/graphql-api/src/app/resolvers.ts:3-12`는 여러 feature/server를 app 레벨에서 병렬 조립한다.
- 한계:
  - 전체 모노레포의 모든 import 그래프를 완전 계산한 것은 아니므로, "모노레포 전체 순환 의존 없음"까지는 주장하지 않는다.

모노레포 전체 수준 결론
- 확인됨: 이 저장소는 "패키지 레이어 구분은 유지하지만, 일부 계층은 placeholder이고 일부 feature는 다른 feature/server에 직접 연결되는 혼합형 아키텍처"로 보인다.
- 재확인 근거:
  - 샘플 영역: `accounts`, `products`, `shared/provider-*`
  - 추가 영역: `search`, `images`, `companies`, `translation`, `apps/graphql-api`
  - 공통 패턴은 ① dual export server 진입점, ② 빈 `export {}` 계층 반복, ③ app의 feature/server 조립이며, 직접 feature 간 server 의존은 현재 읽은 범위에서는 `products-feature`에서만 확인됐다.
