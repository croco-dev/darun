Task 6: Performance 축 진단

정적 분석 기준:
- 실제 프로파일링/번들 분석/응답 시간 계측 없이 코드 구조와 호출 경로만 읽었다.
- 근거 파일: apps/service-web/package.json, apps/graphql-api/package.json, libs/products/feature/src/server.ts, libs/products/feature/src/Product.query.resolver.ts, libs/products/feature/src/Feature.query.resolver.ts, libs/products/datasource/src/index.ts 및 products datasource repository 구현.
- 판단은 "확정 이슈"가 아니라 "성능 리스크 가설" 중심으로 기록한다.

분석 범위 요약:
- service-web은 Next.js 15 + React 19 + Apollo Client 기반 서버 컴포넌트 앱이다. (apps/service-web/package.json)
- graphql-api는 Apollo Server + TypeGraphQL + Drizzle ORM + Mongoose 조합이며, products resolver가 앱 resolver 엔트리에 직접 등록된다. (apps/graphql-api/package.json, apps/graphql-api/src/app/resolvers.ts)
- products resolver 엔트리는 libs/products/feature/src/server.ts에서 Product/Feature resolver를 export하고, datasource 엔트리는 여러 Postgres repository를 export한다. (libs/products/feature/src/server.ts, libs/products/datasource/src/index.ts)

[가설-1] GraphQL Product resolver의 다수 FieldResolver 조합으로 N+1성 호출이 발생할 가능성
- 근거 파일:
  - libs/products/feature/src/Product.query.resolver.ts:198-289
  - libs/products/feature/src/Feature.query.resolver.ts:15-18
  - libs/products/datasource/src/repositories/PostgresqlProductLinkRepository.ts:15-31
  - libs/products/datasource/src/repositories/PostgresqlProductFeatureRepository.ts:15-32
  - libs/products/datasource/src/repositories/PostgresqlProductFeatureScreenshotRepository.ts:15-28
- 관찰:
  - ProductQueryResolver에는 links/tags/screenshots/features/ownedCompany/alternatives/voteCount용 FieldResolver가 분리되어 있다.
  - FeatureQueryResolver에도 screenshots FieldResolver가 있다.
  - links/features/screenshots 계열 일부는 repository 내부 DataLoader로 productId/featureId 기준 배치가 가능하다.
  - 반면 tags는 findOneByProductId 단건 조회 형태이고, ownedCompany/voteCount도 resolver 단에서 개별 use case 호출이다.
- 해석:
  - GraphQL 요청이 product 목록과 함께 tags/ownedCompany/voteCount/features.screenshots 같은 중첩 필드를 요청하면, 항목 수만큼 추가 resolver 실행이 누적될 수 있다.
  - DataLoader가 일부 관계에는 적용되어 있어 완전한 확정 이슈로 단정할 수는 없지만, tags/company/voteCount 경로는 배치 여부가 코드상 바로 드러나지 않아 리스크가 남아 있다.
- 판정: 가설

[가설-2] searchProducts와 alternatives resolver가 "목록 조회 후 개별 상세 재조회" 패턴을 사용해 fan-out 비용을 만들 가능성
- 근거 파일:
  - libs/products/feature/src/Product.query.resolver.ts:159-173
  - libs/products/feature/src/Product.query.resolver.ts:271-285
  - libs/products/datasource/src/repositories/PostgresqlProductRepository.ts:13-29,132-143
- 관찰:
  - searchProducts는 searchProductUseCase 결과 배열을 받은 뒤 searchableProducts.map(...getPublishedProductUseCase.execute({ id }))로 각 상품을 다시 조회한다.
  - alternatives도 추천 결과 배열을 받은 뒤 각 alternativeProductId마다 getPublishedProductUseCase.execute를 다시 호출한다.
  - ProductRepository는 publishedIdLoader를 통해 id 기준 배치를 시도하지만, 상위 use case 레이어가 각 호출을 어떤 스코프로 생성/공유하는지는 이 범위에서 확인되지 않았다.
- 해석:
  - 요청당 DataLoader 인스턴스가 안정적으로 재사용되지 않거나 slug/id 혼합 경로가 섞이면, 검색 결과 수/대안 상품 수에 비례해 DB round trip 혹은 use case orchestration 비용이 늘어날 수 있다.
  - 특히 목록 기반 결과를 다시 단건 상세 조회로 복원하는 구조는 검색 결과가 커질수록 latency fan-out 리스크를 만든다.
- 판정: 가설

[가설-3] locale 번역 로직이 제품 수와 feature 수에 비례해 추가 비동기 호출을 유발할 가능성
- 근거 파일:
  - libs/products/feature/src/Product.query.resolver.ts:63-102
  - libs/products/feature/src/Product.query.resolver.ts:221-259
- 관찰:
  - translateProducts는 products.map(product => this.translateProduct(product, locale))를 Promise.all로 수행한다.
  - translateProduct는 영문 locale일 때 name/description 번역을 병렬 호출한다.
  - features FieldResolver도 각 feature마다 name/summary 번역을 추가 호출한다.
- 해석:
  - 병렬화 자체는 되어 있지만, 번역 저장소/서비스가 원격 I/O라면 결과 수에 비례한 호출 증가가 생긴다.
  - product 목록 + feature 목록을 동시에 조회하는 쿼리에서는 번역 호출 수가 빠르게 증가할 수 있다.
- 판정: 가설

[가설-4] Next.js 페이지의 metadata/body 이중 GraphQL 호출로 동일 slug 요청에서 중복 서버 fetch가 발생할 가능성
- 근거 파일:
  - apps/service-web/app/[locale]/products/[slug]/page.tsx:28-43,99-166
  - apps/service-web/app/[locale]/products/[slug]/alternatives/page.tsx:30-44,98-149
  - apps/service-web/app/[locale]/magazines/[slug]/page.tsx:26-43,83-166
  - apps/service-web/app/getServerClient.ts:9-24
- 관찰:
  - 여러 detail 페이지가 generateMetadata에서 1회, page 본문/JSON-LD 래퍼에서 다시 1회 동일하거나 매우 유사한 GraphQL query를 호출한다.
  - getServerClient는 호출마다 getBaseClient() 후 authLink를 다시 setLink한다.
- 해석:
  - Next.js와 Apollo 캐시가 동일 요청에서 얼마나 dedupe하는지 이 범위에서는 확정할 수 없지만, 코드 구조상 같은 slug/locale로 최소 2회 query 경로가 존재한다.
  - metadata와 본문이 분리된 페이지 수가 늘수록 네트워크/서버 연산 중복 가능성이 누적된다.
- 판정: 가설

[가설-5] service-web의 client/server 경계 혼재로 SSR 경로에서 동적 처리 범위가 넓어질 가능성
- 근거 파일:
  - apps/service-web/package.json:16-18,35-40
  - apps/service-web/app/getServerClient.ts:3-24
  - apps/service-web/app/[locale]/page.tsx:20-27
  - apps/service-web/app/[locale]/products/[slug]/page.tsx:31-43
- 관찰:
  - service-web은 @apollo/client와 experimental-nextjs-app-support/rsc를 함께 사용한다.
  - getServerClient는 static 옵션이 없으면 cookies를 읽어 Authorization 헤더를 붙인다.
  - 홈 페이지는 static: true를 주지만, 상세 페이지 계열은 기본 getClient()를 사용한다.
- 해석:
  - 인증 쿠키 의존 경로는 Next.js 정적 최적화 범위를 줄이고 요청별 서버 연산을 고정시킬 수 있다.
  - 코드상 static/동적 경계가 페이지별로 일관되지 않아 동일한 데이터 특성의 페이지라도 캐시 전략이 달라질 가능성이 있다.
- 판정: 가설

- 없음
- 이유: 실제 번들 리포트, Apollo cache hit rate, DB query count, resolver별 tracing, 응답 시간 수치가 제공되지 않아 확정 판정 근거가 부족하다.

2. detail 페이지의 generateMetadata와 본문 query가 Apollo/Next 캐시로 실제 dedupe되는지 확인
3. 번역 호출 수와 search/alternatives fan-out이 실제 latency에 미치는 영향 측정
