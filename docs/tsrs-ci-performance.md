# tsrs CI 실행 시간·메모리 비교

2026-10-23 GitHub Actions에서 측정했다. [실행 기록](https://github.com/croco-dev/darun/actions/runs/39896478587)의 `tsrs-workspace`, `tsrs-standalone` artifact에 로그와 전체 결과가 있으며, artifact 보관 기간 이후에도 확인할 수 있도록 [개별 측정값](benchmarks/tsrs-ci-2026-10-23.json)을 저장했다.

측정 커밋은 `d23d7669d9158331fcb5364b8307810a892a3704`이다. 모든 측정은 TypeScript 6.0.3을 유지한 상태에서 `tsrs@0.18.0-ts7.1.0-dev.20260929`로 수행했다.

## 적용 설정

PR CI의 전체 패키지 검사는 다음 명령을 사용한다. 측정 당시에는 68개였으며, 최신 `trunk`에서 사용하지 않는 `products/ui` 패키지를 삭제해 현재 검사 대상은 67개다. 아래 수치는 측정 커밋의 결과이며 최신 소스의 실행 시간으로 간주하지 않는다.

```bash
pnpm run typecheck:tsrs --concurrency=4 -- --checkers 1
```

기존 TypeScript 검사와 tsrs 검사는 모두 필수다. 로컬 `pnpm typecheck:tsrs`와 GraphQL·tier-web 단독 CI 검사는 tsrs 기본 옵션을 유지한다. 성능 비교 워크플로는 수동 실행 전용이며 일반 PR마다 반복 측정하지 않는다.

| 68개 패키지 검사             | 시간 중앙값 |     시간 범위 | 최대 메모리 | CPU 시간 중앙값 |
| ---------------------------- | ----------: | ------------: | ----------: | --------------: |
| 기존: Turbo 10 / tsrs 기본값 |     28.04초 | 27.79–28.04초 |     1083MiB |         77.79초 |
| 적용: Turbo 4 / checkers 1   |     25.80초 | 25.74–26.47초 |      734MiB |         70.89초 |

선택한 설정은 측정한 전체 패키지 구성 중 시간 중앙값이 가장 작았다. 기존 설정 대비 tsrs 검사 시간은 **8.0%**, 최대 메모리는 **32.3%** 감소했다. 이 비율은 tsrs 검사 단계의 변화이며 전체 PR 파이프라인의 단축률을 뜻하지 않는다.

`Turbo 4 / --singleThreaded`도 가까운 후보였으나, 중앙값 26.15초·최대 756MiB로 선택한 설정의 25.80초·734MiB보다 높았다. 단일 스레드 설정의 메모리 중앙값은 더 낮았지만, 선택에는 3회 중 가장 큰 메모리 값과 실행 시간을 함께 사용했다. Turbo 동시 실행 수를 1 또는 2로 낮추면 메모리는 더 감소하지만 시간이 늘어났다.

`--maxMemory 256M/512M`, 파일별 검사 시간 캐시, Go 검사 순서와 eager member 옵션도 선택한 설정보다 빠르지 않았다. `--checkerCostCache`는 캐시 준비 전후를 따로 측정했으며, 추가적인 캐시 저장·복원 구성을 도입할 이득을 확인하지 못했다. `--checkerAssignment go --noLazyMembers`는 동일 TypeScript 버전과의 진단 비교 용도이므로 성능 설정에 추가하지 않았다.

단독 실행은 기본값이 가장 빠른 중앙값을 보였다. GraphQL은 0.54초·최대 352MiB, tier-web은 0.70초·339MiB였으며, 스레드를 줄이면 메모리 절약과 실행 시간 증가가 함께 나타났다. 해당 실행기의 메모리 여유를 고려해 기본값을 유지한다.

## 환경과 측정 방법

| 검사 범위             | 실행기 이미지             | CPU                                     |      RAM | Node / pnpm       |
| --------------------- | ------------------------- | --------------------------------------- | -------: | ----------------- |
| 전체 패키지           | `ubuntu22 20261012.322.1` | 4 vCPU, AMD EPYC 7763 64-Core Processor | 15.61GiB | v22.23.3 / 11.2.2 |
| GraphQL·tier-web 단독 | `ubuntu24 20261012.334.1` | 4 vCPU, AMD EPYC 9V45 96-Core Processor | 15.61GiB | v22.23.3 / 11.2.2 |

- 전체 검사는 PR CI와 동일한 Ubuntu 22.04 및 PostgreSQL 17·MongoDB 8 서비스 조건에서 실행했다. 단독 검사는 기존 배포 전 검사와 tier-web CI가 사용하는 Ubuntu 최신 실행기에서 진행했다. 각 범위 내의 모든 설정은 같은 실행기에서 측정했다.
- 전체 16개 구성, 앱별 10개 구성에 대해 순서를 섞어 각 3회 실행했다. 108개 측정 모두 종료 코드 0, 기대한 검사 범위 완료, OOM 0건, 안전 메모리 한도 도달 0건을 확인했다. 초기 워밍업과 캐시 준비 실행은 측정 횟수에서 제외했다.
- Turbo 결과 캐시는 `--force`로 우회하고 모든 패키지는 `--noEmit --incremental false`를 유지했다. 기본 설정으로 워밍업한 뒤 OS 페이지 캐시는 비우지 않았다. `cost-cold`는 매번 검사 시간 캐시를 지우며, `cost-warm`은 같은 옵션으로 캐시를 한 번 준비한 다음 측정한다. 캐시 준비 시간과 향후 Actions 캐시 복원 비용은 warm 측정값에 포함하지 않는다.
- 매번 새 cgroup v2를 만들고 pnpm을 그 안에서 시작하므로 Turbo, tsrs, Next typegen 등 모든 하위 프로세스가 같은 계측 범위에 들어간다. 시간은 명령 실행부터 종료까지의 wall time, CPU 시간은 `cpu.stat`의 누적 사용량이다. tier-web은 기존 `next typegen`도 포함한다.
- 메모리는 `memory.peak`이며 프로세스 트리 전체와 해당 cgroup에 부과된 파일 캐시를 포함한다. 개별 프로세스 RSS의 단순 합이 아니며, CI의 DB 서비스 메모리는 포함하지 않는다. 표의 최대 메모리는 3회 측정 중 최대값이다.
- 측정용 안전 한도는 RAM의 80%와 시작 시 가용 RAM에서 1GiB를 뺀 값 중 작은 값이다. 이 실행에서는 약 12.49GiB였고 어떤 구성도 한도에 도달하지 않았다. `--maxMemory`는 개별 tsrs의 목표치이므로 pnpm·Turbo·Next를 포함한 측정값이 그 숫자보다 클 수 있다.
- 비교는 같은 소스와 고정된 tsrs 버전에 대한 결과다. CI CPU 수·이미지 또는 검사 범위가 바뀌면 다시 측정한다. 단독 작업과 전체 작업은 CPU 모델과 검사 범위가 다르므로 서로의 절대 시간을 직접 비교하지 않는다.

## 재실행

[측정 워크플로](../.github/workflows/TsrsPerformance.yaml)가 기본 브랜치에 반영된 뒤 GitHub Actions의 `tsrs performance`를 수동 실행한다. 결과는 Actions summary와 artifact에 남는다. 측정 실패·누락·OOM이 있는 구성은 유효한 성능 결과로 취급하지 않는다.

Linux에서 측정 도구를 직접 실행할 때는 Node 22, 설치된 workspace 의존성, cgroup v2의 `memory.peak`와 `cgroup.kill`, sudo 권한이 필요하다. coordinator만 root로 실행하며 실제 검사 명령은 sudo를 호출한 사용자로 실행한다.

```bash
python3 -B -m unittest discover -s scripts -p 'test_benchmark_tsrs.py'
sudo -E env "PATH=$PATH" python3 scripts/benchmark_tsrs.py --workload workspace --rounds 3 --output benchmark-results/workspace
```

측정 코드와 원본 로그는 [벤치마크 스크립트](../scripts/benchmark_tsrs.py) 및 위 Actions 실행에서 확인할 수 있다. 계측 정의는 [Linux cgroup v2 문서](https://docs.kernel.org/admin-guide/cgroup-v2.html), 옵션 의미는 [tsrs 성능 옵션](https://github.com/oxc-project/tsrs/blob/main/docs/USAGE.md#performance-options)을 따른다.
